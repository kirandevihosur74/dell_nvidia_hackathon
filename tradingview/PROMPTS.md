## Multi-Provider LLM Orchestration Deep Dive

### (1) Evaluation Criteria

Models were evaluated across four dimensions for each endpoint:

**Latency** — The platform serves real-time trading analysis where seconds matter. For the main chat endpoint (`/api/chat`), users are asking questions while actively watching charts, so sub-3-second first-token response times were required. GPT-4o consistently hit ~800ms TTFT on specialist prompts. For the news endpoint (`/api/get_top_news`), latency was less critical since it loads asynchronously, which opened the door to using a cheaper model.

**Accuracy / Task-Specific Quality** — The 14 specialist personas each carry dense system prompts — the Options specialist alone defines expertise across Greeks, implied volatility surfaces, multi-leg combinations, and position management. These prompts are 300–500 tokens of system instructions. The model needed to hold that entire persona and still reason well about the user's question with injected market data. GPT-4o was the only model that consistently followed the specialist constraints without drifting.

**Cost Per Token** — At GPT-4o's pricing of $2.50/1M input and $10/1M output tokens, a typical specialist chat exchange (system prompt + context + conversation) runs about 2,000 input tokens and 800 output tokens — roughly $0.013 per request. For the news endpoint, which is a simpler retrieval task, GPT-4o-mini-search-preview cut input cost by ~60% while still supporting grounded web search.

**Vision Quality** — Four endpoints use vision (chart analysis, macro image extraction, fundamental image extraction). Chart analysis specifically needs the model to read candlestick prices off the Y-axis, identify support/resistance levels, and map patterns — GPT-4o was the only model accurate enough for this at the time.

### (2) Fallback Routing Logic

A provider-agnostic routing layer in `llm_router.py` abstracts away the backend entirely:

- Two OpenAI-compatible clients are initialized — one pointing to the OpenAI API, one to a local Ollama instance at `127.0.0.1:11434/v1`
- An environment variable `LOCAL_MODELS` defines which model names route locally (e.g., `llama3,mistral`)
- The `chat_completion()` function inspects the requested model name, checks it against the local model registry, and transparently routes to the correct client
- Both clients share the same OpenAI SDK interface, so no endpoint code changes when switching providers
- The main `/api/chat` endpoint accepts a `model` parameter from the frontend (defaults to `gpt-4o`), meaning model selection can also be user-driven at runtime

The key insight was using Ollama's OpenAI-compatible API — the router is just a dictionary lookup, not a complex abstraction layer. Any model that speaks the OpenAI chat completions format plugs in with zero code changes.

### (3) Specific Model Performance Comparisons

**GPT-4o vs GPT-4o-mini for chart vision analysis:** When testing mini on the chart analysis endpoint (which asks the model to "use the vertical axis on the right of the candlestick chart as basis for price"), mini consistently misread price levels by 2–5% and missed secondary support/resistance zones. GPT-4o nailed the exact price readings and identified patterns like head-and-shoulders or double bottoms that mini would overlook or hallucinate. For a trading tool where a $2 misread on SPY means a bad 0dte entry, that accuracy gap was non-negotiable.

**GPT-4o-mini-search-preview vs GPT-4o for news retrieval:** The `/api/get_top_news` endpoint fetches the 5 most recent articles about a stock with fundamental analysis relevance. This is a structured retrieval task — list articles, provide title/URL/summary. Mini with web search performed comparably to 4o because the task is well-scoped (list format, factual extraction, no deep reasoning). Switching to mini saved roughly 60% on input token costs for an endpoint that gets called on every stock page load.

**GPT-4o at temperature 1.0 vs 0.7 for chart strategy analysis:** The chart analysis endpoint uses temperature 1.0, while all other endpoints use 0.7. Higher temperature produced more diverse pattern recognition — at 0.7, the model would consistently identify the same 2–3 patterns and miss less obvious setups. At 1.0, it surfaced a wider range of observations (wedges, flags, channel breaks) that gave traders more to work with, while the structured prompt kept it from hallucinating.

**Local Ollama models (Llama 3) vs GPT-4o for specialist chat:** During development, testing the specialist prompts against Llama 3 via the Ollama router showed the local model could handle basic financial Q&A but degraded significantly on the dense specialist prompts — it would lose the persona constraints after 3–4 conversation turns and start giving generic responses. GPT-4o maintained persona fidelity across 10+ turn conversations. The Ollama path was kept for development iteration and cost-free prompt testing, but production traffic routes to GPT-4o.

### (4) Measuring Quality Systematically

**Dynamic context injection as a quality lever:** Rather than relying on the model's parametric knowledge (which goes stale), a context engine for the main `/api/chat` endpoint dynamically constructs the system prompt with live data from yfinance — current price, 50-day and 200-day moving averages, RSI(14), 1-day/1-month/3-month/6-month/1-year returns, analyst mean rating and price targets, P/E, forward P/E, PEG, price-to-book, beta, index correlations, recent news, and competitor data. Every response is grounded in real numbers, and accuracy can be validated by comparing the model's output against the source data injected.

**Structured output validation on vision endpoints:** The chart and fundamental analysis endpoints extract specific data points (ticker, price, support/resistance levels, valuation metrics). These were validated by comparing extracted values against the yfinance API data for the same symbol. When the model's extracted price deviated >1% from the API price, it was flagged as a miss.

**Prompt-level A/B testing during development:** Each specialist prompt went through iterative refinement. "What to respond to" and "what to avoid" sections were defined in every specialist prompt, then edge cases were tested — asking the Options specialist about crypto, asking the Psychology specialist for trade entries — to verify the model respected boundaries. This was manual but systematic across all 14 specialists.

**Trade execution scoring as a built-in feedback loop:** The `/api/analyze_trade` endpoint asks the model to rate trade execution on a 1–10 scale, analyzing timing, fill price vs. planned price, and risk management. Users see these scores per trade, creating a natural feedback mechanism — if the model's rating consistently didn't match the user's own assessment, it surfaced prompt quality issues.

### (5) Token Budget Optimization

**Hard cap at 1,500 max_tokens across all endpoints.** Financial analysis doesn't need 4,000-token essays. 1,500 tokens (~1,100 words) was the sweet spot — enough to cover a structured analysis with entry/exit points, risk assessment, and rationale, but short enough to keep costs predictable and responses scannable for active traders.

**System prompt token budgets by category:**

| Category | Token Budget | Notes |
|---|---|---|
| Specialist prompts | 300–500 tokens | Static instructions per persona |
| Response guidelines | ~80 tokens | Appended to all specialists |
| Dynamic chat context | 400–800 tokens | Variable — depends on data sections populated |
| Chart analysis user prompts | 150–200 tokens | Structured instructions |
| Trade execution prompts | 200–300 tokens | Dynamic trade data injected |

**Per-request cost breakdown (estimated on GPT-4o pricing):**

| Endpoint | Input Tokens | Output Tokens | Cost/Request |
|---|---|---|---|
| Specialist chat | ~2,000 | ~800 | ~$0.013 |
| Chart vision analysis | ~1,500 + image | ~1,000 | ~$0.020 |
| News retrieval (mini) | ~200 | ~600 | ~$0.001 |
| Trade execution analysis | ~2,500 | ~1,000 | ~$0.016 |

**Context window management:** The dynamic chat endpoint filters out previous system messages before injecting the fresh context-enriched system prompt (`filtered_messages = [msg for msg in messages if msg.get('role') != 'system']`). This prevents system prompt accumulation across multi-turn conversations, keeping input tokens from ballooning as conversations grow.

**Choosing dynamic prompting over fine-tuning:** Fine-tuning 14 specialist models would have cost significantly more in training compute and created a maintenance burden — every prompt update would require a new fine-tuning run. By using detailed system prompts with runtime context injection on a general-purpose model, specialist-quality responses were achieved while keeping the system flexible. Updating a specialist's behavior is a code change, not a training job.
